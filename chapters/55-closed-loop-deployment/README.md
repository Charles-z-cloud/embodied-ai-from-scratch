## 学完以后，你应该能做什么

先修：第21章模型保存、第35章反馈控制、第37章环境接口、第46章动作块、第49章规划、第53章连续动作和第54章评测。你现在会训练模型，但还需要回答：它看到的是多久以前的画面？输出的速度会持续多久？没有新画面时系统怎么办？本章把这些问题放进同一个循环。

遇到新术语时，请先用12岁小朋友都能听懂的语言解释，再给出准确的定义。本章的“部署”，就像把练习好的司机放进驾驶座，接上方向盘和实时路况；准确地说，是把模型连同输入处理、输出转换、运行资源和故障处理接入实际执行系统。部署不以“成功加载权重”为结束。

## 1. 一次控制循环到底做了什么

沿用第52章二维桌面：读相机图像和自身位置 → 计算红蓝目标的像素重心 → 读指令 → 模型给速度 → 检查速度 → 积分更新位置 → 再拍图。

```mermaid
flowchart LR
  A[带时间戳的图像和位置] --> B[预处理与输入检查]
  B --> C[策略推理]
  C --> D[动作解码与单位转换]
  D --> E[限幅和异常处理]
  E --> F[执行一个控制周期]
  F --> A
```

这里的预处理必须和训练一致。训练用RGB、范围0到1、通道在前，部署却传BGR、范围0到255、通道在后，即使形状碰巧能算，也不等于信息正确。归一化参数也应来自训练集。动作必须注明它是位置、位移、速度还是力；把每秒0.5米解释成每步移动0.5米，在0.1秒的周期下就会大十倍。

本章沿用速度命令，单位米每秒，坐标范围是教学场景规定的米制范围。执行器采用第37章的理想积分关系，不包含真实电机响应。

## 2. 为什么时间也是模型输入的一部分

“延迟”就像你看见的球其实是半秒前的球；准确地说，是从信息采集到被用于控制之间的时间差。令采集时间为 $t_s$、执行命令时间为 $t_e$，信息年龄为：

$$
\tau=t_e-t_s.
$$

流水线串行执行时，年龄可能包含采集、传输、预处理、推理和等待执行的时间。并行流水线有重叠，不能不加判断地把各段平均耗时相加。还要看最慢情况和耗时分布，平均10毫秒并不意味着每次都能在10毫秒内完成。

“控制频率”就是一秒改几次命令，准确地说是单位时间的控制更新次数。固定周期 $\Delta t=0.1$ 秒对应 $f=1/\Delta t=10$ 赫兹。相机、策略和底层电机可以有不同频率；例如相机提供一张图后，底层控制器可能更新很多次。但旧图不会因为重复使用而变新。

若位置沿某轴速度不超过 $v_{\max}$，没有外部跳变，则旧位置与当前位置差的保守上界是 $v_{\max}\tau$。以0.5米每秒、0.2秒延迟为例，是0.1米，已经大于本实验0.09米的成功半径。若存在外力扰动，这个简单界就不再覆盖全部误差。

## 3. 缓冲区、动作块和重新规划

“缓冲区”像一个临时收件箱，准确地说是等待处理的数据存储队列。处理每一张旧图未必合理：如果相机每秒30张而模型每秒只能处理10张，按到达顺序逐一处理会不断积压。控制任务常需要消费最新可用观测，同时记录丢弃了多少旧数据。数据记录任务却可能要求保留完整序列，两者目标不同。

动作块是第46章的连续若干动作。块长为 $H$、每步周期 $\Delta t$ 时，完整执行它要 $H\Delta t$ 秒。重新规划每 $K$ 步发生一次，意味着每次先执行块的前 $K$ 步；$K$ 不必等于 $H$。长块减少推理次数，却让系统更久不能根据新情况修正。异步计算时还必须处理“新块准备好前旧块用完”和“新块到来后旧块剩余动作如何处理”。本章实验使用单步动作，避免把动作块和通信延迟两个因素混在一起。

## 4. 异常处理也必须有明确语义

“看门狗”就像发现司机太久没回应就提醒停车的人，准确地说是检查系统是否在规定时间内更新的监测机制。这里规定：没有观测，或者观测年龄超过3个周期，就输出零速度。注意“超过3”意味着年龄恰好3仍可用。

我们还检查动作形状为2、数值有限，再限幅到每轴正负0.5。不能用限幅代替有限性检查：NaN表示无效数，比较和算术会传播异常。无效动作在本实验中替换为零并记一次错误。

零速度只在这个直接控制位置积分的玩具环境里有停止含义。真实机械臂的重力、惯性、夹持物和底层控制模式决定了正确停机方式，需要设备自己的控制接口和停机设计。本教材的零向量不是可直接移植到所有机器人的停机方案。

恢复运行也不能只看“又来了一包数据”。应检查时间戳、坐标系、传感器状态以及任务是否仍有效。本实验仅演示数据重新变新后恢复控制，不实现真实设备恢复协议。

## 5. 实验：给成功策略加入通信故障

运行前完成第52、53章，生成相应权重。激活全书环境后，从仓库根目录运行：

```bash
python chapters/55-closed-loop-deployment/examples/deployment.py
```

脚本比较两个冻结策略：根据当前收到的目标重心计算速度的几何控制器，以及第53章连续回归策略。二者得到完全相同的延迟观测，不给几何控制器额外的真实目标坐标。

40个评测种子为300—339，使用已见组合区域。条件依次为无故障、延迟2步、随机丢30%帧、延迟加丢帧加位置扰动、延迟5步以及注入一次无效动作。每种条件独立重置，丢帧随机数固定。最后两个条件专门验证超时保护和动作检查是否真正生效。

动作执行关系为：

$$
p_{k+1}=\operatorname{clip}(p_k+0.1a_k,-1,1).
$$

$p_k$ 是二维位置，$a_k$ 是检查后的二维速度，外层裁剪代表场景边界。到原指令所指目标距离小于0.09算成功，最多100步。丢帧实验不是训练数据增强；本章不再更新权重。

脚本按模拟步数安排观测到达，因此比较的是**人为设定的通信年龄**。Python真正计算耗时并不自动推进这个仿真时钟；不能把结果称为真实端到端实时性能。输出中记录成功率、平均步数、平均过期停止次数和无效动作次数。失败意味着100步内未成功，具体原因需要结合停止计数和轨迹分析，不能把所有失败都归给模型。

[实际结果和运行范围](validation.md)记录本次结果。先预测“延迟5步、最多允许3步”会发生什么，再运行。这样是在检验自己对系统的理解，而不是只看一张成功率表。

## 6. 从仿真到实物，还缺哪些证据

“仿真到现实差距”像游戏里的车和真实汽车不同，准确地说，是模拟环境与真实环境在观测、动力学、时序和任务分布上的差异。我们理想化了瞬时速度响应、准确位置反馈、无碰撞和固定颜色。它们都可能在实物上失效。

合理的下一步是先做离线输入回放，确认预处理和动作单位；再在仿真中加入时序和动力学变化；再用真实设备的只读传感器模式确认时间戳；最后根据具体设备逐步开展受控运行。每一步分别记录通过标准和失败，不用玩具实验100%成功替代真实验证。

可阅读[LeRobot官方仓库](https://github.com/huggingface/lerobot)中机器人接口、观测读取、动作发送与策略推理的组织方式。本章没有安装或运行LeRobot，也没有连接硬件。阅读时画出输入到执行的调用链，指出单位转换和时间控制发生在哪里，比直接复制一条部署命令更有学习价值。

## 过关标准

你能指出一个动作何时生成、基于哪一帧观测、以什么单位持续多久；能解释过期数据为什么不能无限重用；能区分模拟延迟和墙钟耗时。达到这些标准后，再进入下一章的论文复现方法。
