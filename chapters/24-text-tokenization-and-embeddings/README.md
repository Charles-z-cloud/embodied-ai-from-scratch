## 为什么学习具身智能还要学NLP

机器人看到红蓝方块，只解决了“看见什么”。要理解“把红块移到蓝块左边”，还得处理文字的内容、顺序和指代。**自然语言处理**（Natural Language Processing，NLP）研究让计算机处理人类语言的方法，涵盖表示、理解、生成等任务。

你不必先学完所有传统NLP专题才接触VLM，但词元化、嵌入、序列建模、注意力和语言模型训练是主线必需知识。本章从最基础的“怎样把字符串送进模型”开始；先修是字符串、字典、数组、分类和PyTorch。

## 1. 字符、词和词元不是同一个东西

**词元**（token）像把一句话切成可编号的小积木。准确地说，它是特定分词规则输出的基本处理单位。一个词元可能是一个字、一个词的一部分、完整单词、标点、空格，甚至字节片段；不由“人眼觉得这是一个词”唯一决定。

**词元化**（tokenization）是把文本切成这些单位的过程。中文“拿红块”可以按字符切成“拿/红/块”，也可以按词切成“拿/红块”；英文 `playing` 可以整体一个词元，也可能被切成子词。**子词**就是比完整词更小、可重复组合的片段，有助于处理训练时没见过的长词或新词。

本章的字符分词用 `list(text)`。严格说，Python遍历字符串得到Unicode码点，不总是人眼所见的一个完整字符：有的emoji或带组合符号的文字由多个码点组成。本例只用常见汉字和简单英文，因此可把它当作字符入门，不把这个简化扩展到所有语言。

同一句文本在不同分词器下词元数不同，因此“大概多少字”等于“多少token”没有固定通用比例。

## 2. 词表与编号：先有规则，再编码

**词表**像给每种积木发一个号码的登记册，准确地说，是词元与整数ID的映射。**编码**把词元序列换成ID序列；**解码**按同一词表把ID还原为文本或词元。

本章保留四个特殊编号：

| 词元 | 编号 | 直观含义 |
|---|---:|---|
| `<PAD>` | 0 | 补齐空位，不是真实文字 |
| `<UNK>` | 1 | 当前词表不认识的输入 |
| `<BOS>` | 2 | 一条序列开始 |
| `<EOS>` | 3 | 一条序列结束 |

特殊词元是模型输入协议的一部分，不是所有模型都采用这些名字或编号。其他字符从4开始，按固定排序编号以便复现。

ID只是名字，没有数值距离含义。红字ID为10、蓝字为20，不能据此说蓝色比红色大一倍。训练好的模型必须配同一词表和预处理规则，随意重新排序词表会让向量查表含义全部改变。

构造自己的词表时只使用训练文本，评测文本出现的新字符按事先约定处理。若使用已有预训练模型，直接使用它配套的固定分词器，不需要根据你的测试集重建。

## 3. 未知词元与可逆性

如果本章词表只见过红蓝指令，遇到“黄”就会用 `<UNK>`。这样程序还能继续运行，但信息已经丢失：黄色和紫色都可能变成同一个未知编号，解码无法恢复原字。

若没有未知符号、没有删除或规范化文本，本章字符编码应满足 `decode(encode(text)) == text`。**文本规范化**像先统一写法，例如统一大小写、空格或某些Unicode形式；它可能是有意的，但会影响是否能原样还原。预处理不是无关紧要的清洁步骤，它决定模型看到的内容。

真实分词器可能使用字节级编码避免某些未知字符问题，但代价可能是序列更长；不能简单宣称有子词就永远不会出现未知情况。

## 4. BPE：把经常相邻的小积木合起来

**字节对编码**（Byte Pair Encoding，BPE）最初是一类合并常见符号对的压缩方法，在NLP中常用于学习子词词表。可以先想成：如果两块积木总是挨着出现，就把它们做成一个更大的积木。

本章演示一个简化的字符级版本，流程是：先把每个训练词拆成字符；统计相邻词元对出现次数；选择最常见的一对并合并；重复固定轮数。遇到次数相同，使用固定排序决定，保证输出可复查。

例如训练列表 `low, low, lower, lowest` 中，“l,o”和“o,w”都很常见。先合成“lo”，再把“lo,w”合成“low”，随后可以合并其他重复片段。新词仍可以由已有小片段拼接，不必把每个完整词都放进词表。

推理时使用训练已经学到的有序合并规则，不能每收到一句指令就重新统计并学习另一套规则。本例逐个英文词处理，不跨单词边界，不含字节编码、完整Unicode规范化和生产级特殊符号协议；它只展示核心合并机制。[子词BPE的经典论文](https://arxiv.org/abs/1508.07909)

## 5. 独热向量与embedding查表

第16章用过独热类别标签。若词表有 $V$ 个词元，ID为 $i$ 的词元也可用长度V的独热向量 $e_i$ 表示。但当V很大时，绝大多数位置都是0，直接保存不划算。

**嵌入**（embedding）可以先理解为给每个词元准备一小串可学习数字作为描述。准确地说，维护参数矩阵 $E\in\mathbb R^{V\times d}$，输入ID为i时取第i行：

$$
x_i=E[i]=e_i^\top E.
$$

$d$ 是嵌入维数。查表等价于独热向量乘矩阵，但无需真的构造一整排0。嵌入是模型参数，可以在训练时通过梯度调整；一个词元出现多次，对同一行的梯度贡献会累加。

PyTorch写 `nn.Embedding(V,d)`。输入ID类型为long，形状 `(B,T)`，输出形状 `(B,T,d)`，其中T是序列长度。[PyTorch Embedding](https://docs.pytorch.org/docs/2.14/generated/torch.nn.Embedding.html)

随机初始化的嵌入没有自动理解“红”和“蓝”的含义。相似性需要通过训练任务形成，而且嵌入距离受训练数据与目标影响。只做一次查表不等于语言理解，也还没有处理词元顺序。

## 6. 不同长度怎样组成一批

三条指令可能长短不同，但一个规则数组需要矩形形状。**填充**padding就是给短序列补 `<PAD>` 到同一长度。**截断**truncation则把超过上限的部分按规则裁掉，可能丢失关键信息；不能无记录地截掉“不要”或目标物体名。

**掩码**mask可以先理解为一张“哪些位置有效”的真假清单。对ID数组，`mask = ids != pad_id` 给出有效位置。嵌入层设 `padding_idx=0` 时，该行按默认初始化为0，且不通过普通嵌入反传更新；但后续层仍需要掩码，尤其有偏置、序列计算或求平均时，不能靠0向量自动解决全部填充问题。

如果要对内容词元向量求平均，应排除PAD与本例的BOS/EOS：

$$
\bar x_i=\frac{\sum_{t=1}^{T}m_{i,t}x_{i,t}}{\sum_{t=1}^{T}m_{i,t}}.
$$

$m$ 是0/1掩码，分母是有效内容长度，必须大于0；空指令应按规则拒绝或单独处理。代码把mask扩成 `(B,T,1)`，才能与 `(B,T,d)` 广播相乘。

下一章模型要预测下一个词元，损失也应排除填充位置；第26章注意力还会需要另一种限制可见位置的掩码。它们的目的不同，届时分别解释。

## 7. 词袋基线为什么看不懂左右关系

**词袋**（bag of words）像把一句话拆成积木倒进袋里，只数每种有多少，不记录排列。准确地说，常用一个V维计数向量记录各词元出现次数。它可以作为简单文本分类基线，但天然丢失顺序。

“红块在蓝块左边”和“蓝块在红块左边”有完全相同的字符计数，却表达相反的空间关系。任何只接收该计数向量的确定性分类器，都无法区分这两条指令，因为输入已经完全相同。

平均词元嵌入也有同样的顺序问题：对同一组向量调换顺序，平均值不变。下一章引入序列模型，就是为了让“先后位置”真正参与计算。视觉语言模型必须同时处理图像内容与语言关系，不能只发现“红、蓝、左”几个关键词就当理解了任务。

## 8. 运行编码、查表与BPE

```bash
python chapters/24-text-tokenization-and-embeddings/examples/text_basics.py
python chapters/24-text-tokenization-and-embeddings/examples/simple_bpe.py
```

第一个脚本建立并保存字符词表，检查已知指令往返、未知字符、不同长度填充、嵌入形状和带掩码平均；还证明两句相反关系的词袋完全相同。嵌入权重仅随机初始化，本章不声称训练语义表示。

第二个脚本打印合并规则和新词拆分。Python `Counter` 是标准库中的计数器，像默认值为0的字典，方便统计词元对；`zip(tokens,tokens[1:])` 将每个词元与紧邻的后一个配成对。推理按照同一个合并顺序执行。

排序中的 `lambda p: (-counts[p], p)` 是一个简短的匿名函数，等价于定义函数返回这个二元组：先按负次数排序，让高频在前，再按词元对排序处理平局。此BPE脚本只演示片段合并，允许未见字符保留为字符；它没有实现完整固定词表的ID编码和字节回退，不能直接当作生产模型的分词器。

后续可参考 [Hugging Face Tokenizers 文档](https://huggingface.co/docs/tokenizers/index) 查看真实工具的编码、解码与预处理流程。核验日期2026-10-24；本章实际运行自编字符与简化BPE实现，未安装或运行该外部库。
